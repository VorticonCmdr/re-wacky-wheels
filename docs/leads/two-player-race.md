# Two-player split screen and shoot-out in the race engine (WF lead, 2026-10-05)

## 0. Naming correction (read first) and conventions

The task text called [0x28be2] the two-player flag and [0x28bdc] the shoot-out flag. The code says the opposite (and docs/leads/racer-states.md 9.1 and the claims `racer.start-grid` / `route.placement-observed` already agree with the code):

* **[0x28bdc] != 0 = TWO PLAYER RACE** (laps, ranking, finishing; the menu stores the choice of "RACE HEAD TO HEAD" = 1 or "RACE WITH ALL CARS" = 2 there: obj1+0xfd14 (menu 0x55c0), +0xfd6e..+0xfd74). Evidence in the engine: the progress/lap routine obj1+0x2b44 and the computer racers' step are only called when [0x28bdc] != 0 (obj1+0x22768 jz 0x227a0 skips both); the end-of-round text is "WHAT A CRASH!" (obj2+0x19d8) when [0x28bdc] != 0 and "THAT WAS A DOUBLE KILL!" (obj2+0x19e8) otherwise (obj1+0x2127e to +0x2129a).
* **[0x28be2] != 0 (with [0x28bdc] == 0) = TWO PLAYER SHOOT-OUT** (no laps, no computer racers, first to n hits). It is set to 1 by the shoot-out menu entry obj1+0x1017a.
* **[0x28bde] != 0 = the split screen itself.** It is 1 whenever [0x28be2] or [0x28bdc] is set (obj1+0x7965 to +0x7973) unless the link word [0x28c0c] is not 0 (then it takes [0x28bd0], obj1+0x7984 to +0x798c). Link play ([0x28c0c]: "WAITING FOR PLAYER", modem/serial) is NOT covered here.

Names used below: P1 = racer/car 0 = the human of the main loop = the **bottom** half; P2 = racer/car 1 = the second human = the **top** half. Car record n = obj2+0x8410 + 0x104 n (pointer [0x1d5c0] car 0, [0x1d5bc] car 1, current car [0x1d5b0]). Racer record n = obj2+0xaa90 + 0x68 n. "Frame" = one pass of the loop obj1+0x21021 .. +0x227a5 (racer-states.md section 0). Screen: mode X, 80 bytes a row, pages [0x28b24] = 0 / 0x3e80; row r of a page is byte 80 r. All screen positions are (x column, y row) of the 320x200 screen.

## 2. Per-frame order

### 2.1 One screen (for comparison), the loop obj1+0x21021
1. loop head: [0x1ed6c] = [0x1ed74] = 0, tick latch, key polls (obj1+0x21021 to +0x2110d).
2. scene: `call 0x18480` (view cone box + sin/cos of the heading; obj1+0x18480 to +0x18667), floor/horizon copy `0x27e94` (if [0x1eb80]), draw group `0x18998` = compass frames 0x187ec, racers 0x155d4, static objects 0x15a78, own car 0x16a3c, starter 0x166a8 (if [0x28c38]), shots 0x1632c, sort + blit 0x153d8 (obj1+0x2108b to +0x210b2, +0x18998 to +0x189e4).
3. `call 0x1f794` once a frame ([0x1ed74] guard, obj1+0x210b7 to +0x210c0): 0x18668 (palette cycling, GAM flag [0x28b60]), contact routine 0x1d3fc, flash effect [0x28c8c], then HUD 0x1a92c (obj1+0x1fb6e), animation counters 0x161fc, held item 0xdd8, and, when [0x28c42] > 1 (the one-screen crash / drive-away state), sound 0xb once plus `0x12034` (obj1+0x1fc4e to +0x1fc75; not a countdown sound).
4. page flip 0x27de0, page toggle [0x28b24], frame limiter [0x1ea5c], frame counter `inc [0x1ec64]` (obj1+0x210c5 to +0x2114c), keys.
5. end checks (obj1+0x21229 to +0x22592): finish, pause menu, retry menus.
6. logic group obj1+0x22593 to +0x227a5: tick latch, 0xd04, input 0x1d6d0, car step 0x190a0, car point -> racer 0, fire 0x14364, [AI step 0x18cac when [0x28c44] == 2, progress 0x2b44 unless duck], shots 0x1602c, `jmp 0x21021`.

### 2.2 Two player / shoot-out: what is added
**Draw side (inside `call 0x1f794`, obj1+0x1f919 to +0x1fb6d), after viewer 0 has been drawn by step 2 above** (so the order is: viewer 0 scene = bottom half, then viewer 1 scene = top half, then the HUD for both):
1. save viewer 0's context and load viewer 1's: [0x28b0a], [0x28b0e] -> [0x28c6e], [0x28c72] and [0x28ca2], [0x28ca6] -> [0x28b0a], [0x28b0e]; [0x28b96] -> [0x28c76] and [0x28c6a] -> [0x28b96]; [0x1d860] -> [0x1d898] and [0x1d840] -> [0x1d860]; [0x1d5d4] := racer 1 +0x50 (obj2+0xab48); [0x1d5b0] := [0x1d5bc]; [0x28b7e] := 1 (obj1+0x1f93b to +0x1f9a6).

6. HUD `0x1a92c` once for both (obj1+0x1fb6e), `0x161fc`, then **a per-player block** (obj1+0x1fb9e to +0x1fc35): for p = 0, 1: [0x28b34] = 0x2260 (row 110), minus 100 x 80 for p = 1 (= 0x320, row 10); when car p +0x14 (the inverted-controls flag) is set and the slot is active: `call 0x26ec2` = a **vertical flip of the 90 viewport rows** (obj1+0x26ec2 to +0x26f13: copies rows bottom to top through the scratch page 0xbb80 and back); the flag is cleared after 0x12c (300) frames from car +0x8a (obj1+0x1fc07 to +0x1fc1d). This block is skipped in a one-screen race (obj1+0x1fb86 to +0x1fb98).
7. `call 0xdd8` (held item icon, both players), etc.

**Logic side (obj1+0x22593 to +0x227a5), in order:** viewer 0 input 0x1d6d0, step 0x190a0, racer 0 x/y := car point [0x28b68]/[0x28b6a] (obj2+0xaaa6/+0xaaa8), racer 0 heading +0x50 := [0x1d5d4], fire 0x14364 (obj1+0x225b2 to +0x225de); then, when [0x28be2] or [0x28bdc]:
* swap in viewer 1 (same words as above, plus [0x28ce0] := [0x28cdf], [0x28cd5] := [0x28cc3], [0x28cdd] := [0x28ccc], [0x28b40..46] := the bytes [0x28cc4..7]) and [0x28b7e] := 1 (obj1+0x225fb to +0x22692);
* input 0x1d6d0 and step 0x190a0 again (obj1+0x226ca, +0x226cf); racer 1 x/y (obj2+0xab0e/+0xab10) := car point; viewer 1's camera and heading saved ([0x28ca2], [0x28ca6], [0xab48], [0x1d840]); **fire 0x14364 again** (obj1+0x22718); then viewer 0 restored, [0x28b7e] := 0 (obj1+0x2271d to +0x22763);
* only when [0x28bdc]: the computer racers' step 0x18cac if [0x28c44] == 2, then the progress routine 0x2b44 (obj1+0x22768 to +0x22781, +0x2279b); with [0x28be2] alone neither is called;
* shots 0x1602c and the loop jump as before.

Not called by anyone (no `call`/`jmp` operand in obj1.asm): obj1+0x2678 (swap in viewer 1), +0x26f4 (save viewer 1), +0x2724 (restore viewer 0): the same swaps exist only as inline copies at obj1+0x3531 to +0x3662 (the first-frame renderer `0x33d8`: viewer 0, then viewer 1 through the same swap, then the restore), +0x1f93b and +0x225fb.

## 3. Split-screen layout

### 3.1 The screen (rows of the 320 x 200 page)
| rows | content | cite |
| --- | --- | --- |
| 0 to 9 | the picture strip (sky) of the top half; P2's driver name at (4, 1) | obj1+0x3000 to +0x305f |
| 10 to 29 | viewer 1 horizon strip (20 rows) | obj1+0x2c427 (edi = 0xa0000 + 0x320) |
| 30 to 99 | viewer 1 floor (70 rows) | obj1+0x2c524 (edi = 0xa0000 + 0x1ef0 = row 99, rays drawn upward) |
| 100 to 109 | the picture strip of the bottom half; P1's driver name at (4, 101) | obj1+0x3064 to +0x30b5 |
| 110 to 129 | viewer 0 horizon strip (20 rows) | obj1+0x27ed3 (0x2260) |
| 130 to 199 | viewer 0 floor (70 rows) | obj1+0x27fdd (edi = 0xa0000 + 0x3e30 = row 199) |

* So each half is a **90-row viewport (20 horizon + 70 floor) of 320 columns; viewer 0's viewport is exactly the one-screen viewport (rows 110 to 199), and viewer 1's is the same picture 100 rows higher.** The one-screen sky picture (rows 0..109) is not used: the 10-row strip above each viewport (rows 0..9 and 100..109) comes from a different background picture, `BLANK.PCX`, below.
* The background picture of a split game is `BLANK.PCX` (obj2+0x1548): when ([0x28be2] or [0x28bdc]) and [0x28bde], the loader overwrites the sky name buffer obj2+0xa4e0 (normally GAM line 5) with "BLANK.PCX" (obj1+0x1746d to +0x17495). Decoded from the user's archive (read-only): BLANK.PCX is 320 x 200, colour 46 (0x2e) everywhere except two small identical pictures in the rows 0..9 and 100..109 at columns about 123..258 (index 46 is also the colour of the boxes the HUD draws, section 3.5). The art itself was not identified.
* The one-screen sky and the minimap panel are therefore absent; in a split game the strips carry the driver names, the SCORE boxes (shoot-out) and that small picture.

### 3.2 Floor / horizon renderer per viewer
* Viewer 0 uses the one-screen routine obj1+0x27e94 (dispatch on [0x28c20] at +0x27eaa: 1 -> +0x27ece, 2 -> +0x295dd, else +0x2ad0f); viewer 1 uses the copy obj1+0x2c3e9 (1 -> +0x2c422, 2 -> +0x2db24, other -> +0x2f22d). In all three detail levels the copy is the same code with the destination moved 100 rows (8000 bytes) up: horizon copy destination 0x320 instead of 0x2260 (obj1+0x2c427, +0x2db29, +0x2f232 vs +0x27ed3, +0x295e2, +0x2ad14) and the floor start 0x1ef0 instead of 0x3e30 (obj1+0x2c524, +0x2dc26, +0x2f328 vs +0x27fdd, +0x29708, +0x2ae0a).
* Parameters are identical for both viewers (checked for the 320-ray level by counting): 70 floor rows per ray (the 70 `sub edi,0x51` blocks obj1+0x28049 to +0x29594 and obj1+0x2c590 to +0x2dadb), the same distance table [0x1d660] (70 dwords, `mul dword [esi]`), rays 320 / 160 / 80 (`mov ecx,0x140` obj1+0x27fec, 0xa0 obj1+0x29717 and +0x2dc35, 0x50 obj1+0x2ae19 and +0x2f337), angle = camera heading - 0xa0 stepping 8 table bytes a ray (obj1+0x27fae to +0x27fd2, wrap at [0x1d698] -> [0x1d6a0]), world point = ray vector x distance + camera ([0x28b0a], [0x28b0e]). There is no per-viewer camera height or scale: **only the camera x/y, heading, the horizon tilt pointer and the destination rows differ.** Negative finding (tool: awk over the operand text of obj1.asm, 2026-10-05): the whole floor / horizon code obj1+0x27e94 to +0x30905 contains no reference to [0x28b7e], [0x28bde], [0x1ed30], [0x28be2] or [0x28bdc]; it reads only the camera words [0x28b0a]/[0x28b0e], the heading [0x1d5d4], the horizon pointer [0x1d860] and the page [0x28b24]; **the choice of viewer is made by the caller** (obj1+0x1f9c3 to +0x1f9d4, and obj1+0x35b3 to +0x35c4) picking `0x2c3e9` or `0x27e94` after the swap.
* Horizon strip: 20 rows copied with `rep movsb` in write mode 1 (latch copy; obj1+0x27e96 to +0x27e9e) from the off-screen strip at VRAM 0x7d00 + (one of four row offsets 0, 0x50, 0xa0, 0xf0): the pointers [0x1d824], [0x1d828], [0x1d82c], [0x1d830] = 0xa7d00, 0xa7d50, 0xa7da0, 0xa7df0 (obj1+0x26789 to +0x267a7); the live pointer is [0x1d860] (viewer 0) / [0x1d840] (viewer 1), both initially 0xa7d50 (obj1+0x267b1, +0x267bb), nudged by car +0x52 / +0x54 (the look-down / look-up counters of a hop) in `obj1+0x14834` (called from obj1+0x13d51, +0x13e71, +0x20a09), clamped to the four values.
* The view cone box [0x28c16..0x28c2c] and sin/cos [0x1d614], [0x1d5e4] come from the viewer's heading in `0x18480` at the start of each viewer pass (obj1+0x18480 to +0x18663): cone corners at distance 0x462 and heading +- 0xa0.

### 3.3 Sprites and objects per viewer
* Each viewer pass rebuilds the draw list: record count [0x28b78] = 0 and cursor [0x1d86c] = 0x19a28 (records of 0x28 bytes), then racers (0x155d4), static objects (0x15a78), own car (0x16a3c), starter (0x166a8), shots (0x1632c), sort (bubble sort on the dword +0x10, larger first: obj1+0x15430 to +0x15484), then the object pass 0x12bf4 and the blits (obj1+0x15486 onward).
* **All positions are computed in one-screen coordinates (rows 110 to 199: the racer's y is clamped to at most 0xc7 = 199 and to at least 0x6e = 110 when airborne, obj1+0x158d4 to +0x158f7; crop rows obj1+0x15990 to +0x159c1), and the blit subtracts [0x1ed30] = 100 rows for viewer 1** when the two-player flag in edi is set (obj1+0x14bd9 to +0x14bed set edi = 1 for [0x28be2] or [0x28bdc]; the subtraction `if [0x28b7e] != 0 and edi != 0` is at obj1+0x14c33 to +0x14c4f, in the second blit routine at obj1+0x15545 to +0x1555a). So sprites cannot spill into the other half.
* **The viewer's own racer is skipped:** the racer loop skips racer index == [0x28b7e] (obj1+0x155f8 to +0x1560f; the intro word [0x28ca8] is 0 in a race). So viewer 0 sees racer 1 (the other human) and the computer racers; viewer 1 sees racer 0 and the computer racers. The own car is a separate draw record (type +0x24 = 0, +0x18 = the viewer index, key +0x10 = 0x7c; obj1+0x16e4d to +0x16eb3).
* Distance rules for a racer in the list are racer-states.md 2.1 (box words [0x28c16..], cone test 0x14a08, distance 0x50 to 0x462, size class (d - 0x7c) / 0x46 at most 9).

### 3.4 The other human's car as the viewer sees it
* Compass frame: `0x187ec` (the loop obj1+0x18875 to +0x18984): sector word [0x28c30] from the viewer's heading ([0x1d5d4] / 0xf0 rounded, obj1+0x187f7 to +0x18875), then for every racer: **when [0x28be2] is set, for every racer; when only [0x28bdc], for racers 0 and 1 (index < 2)** `call 0x1876c` (obj1+0x1889e to +0x188bc), which rebuilds the racer's compass word +0x1a from the racer's own heading dword +0x50: sector = +0x50 / 0xf0 rounded to the nearest (remainder >= 0x78 rounds away from the quotient, obj1+0x1877a to +0x187d3) and the word at obj2+0x1d328 + 2 sector (obj1+0x187da). Then the frame word = word at obj2+0x106a0 + 16 x (viewer's sector) + 2 x (+0x1a), stored at racer +0x38 + 2 x [0x28b7e] (obj1+0x188c7 to +0x188ef). Computer racers keep their route compass word.
* Racer heading of a human: racer 0 +0x50 := [0x1d5d4] every frame (obj1+0x225d4 to +0x225d9), racer 1 +0x50 := its saved heading (obj1+0x22704 to +0x22709, +0x1fa49 to +0x1fa4e). A human racer's x/y is its car point (the point 0x7c ahead of its camera, [0x28b68]/[0x28b6a], obj1+0x225bc to +0x225ce, +0x226d4 to +0x226e6; start: obj1+0x205dc to +0x2061e), not the camera.
* Picture: normal case = the CARS.SP slot record frame `[0x13c08 + 0x98 x slot (+0x26) + 4 x frame]` with the frame at `+0x38 + 2 x [0x28b7e]` (obj1+0x157e1 to +0x15807). **Override for a human racer** (obj1+0x15823 to +0x1587d): when [0x28be2] or [0x28bdc] is set and the car word +0x44 (obj2+0x8454 + 0x104 n) is not 0 and the car's +0x7e (wrecked) is 0, the size table is `[0xe560 + 4 x size class]` and the picture is the car record's own animation: dword car +0x64 (obj2+0x8474) + 0x300 x car +0x5e (obj2+0x846e), i.e. 8 frames of 0x300 bytes (32 x 24). Car +0x44 is set to 1 at obj1+0x14271 (in the routine obj1+0x14200 to +0x14296 that plays sound 0xf SPLASH, stores [0x28bd8] := the terrain id and reads the picture base from the SDX record +0x12a): so it is the water/splash animation state; the own car uses the same frames (obj1+0x16af0 to +0x16b21, wrapping at 8, obj1+0x16b27).
* A racer with word +2 = 2 (wrecked, section 4) draws the crash pictures obj2+0x1c7f0 + 4 x (+0x56), and is not drawn once +0x56 > 3 (obj1+0x157b4 to +0x157ca); stun (+0x58 = 1) uses frame +0x5a (obj1+0x157d3, +0x15809).

### 3.5 HUD (one routine, obj1+0x1a92c, drawn once per frame for both players; the static part obj1+0x2f80 once per round)

### 4.3 What a shot does to a human in the shoot-out

* In the shoot-out (or duck) a type 5 shot (ice) is changed to type 0 (obj1+0x11a7f to +0x11a98).
* Human branch (obj1+0x11b87 to +0x11dc3): a human already wrecked has racer +2 = 2, so the loop skips it at obj1+0x11985 and the shot passes through the wreck; the car +0x7e test at obj1+0x11b87 to +0x11b9a (absorb, result 3) only matters while +0x7e is set and +2 is not 2. **With [0x28be2] set and shot type <= 2 (types 0 hedgehog / fireball, 1 devils, 2 bomb, and the converted ice): the human is wrecked outright** (obj1+0x11ba2 to +0x11c65): sound 0xd BOOM; racer +0x56, +0x58, +0x5c = 0 and racer +2 = 2; voice handle car +0xd4 freed (when [0x1ecf8]); car +0x7e = 1 and car +0x44, +0x20, +0x3c, +0x18, +0x42 = 0; result word [0x28bae] = 3 (shot consumed).

### 4.4 The round: wreck animation, message, score, respawn (all in the frame routine, obj1+0x21229 to +0x2149d)
1. **Wreck animation.** The wrecked human's own pass draws its car as the crash pictures: when car +0x7e != 0 and [0x28c42] == 0 the picture is `[0x1c7f0 + 4 x racer +0x56]`, and `racer +0x56` is incremented there every frame (obj1+0x16d12 to +0x16d52); once +0x56 > 3 the car is no longer drawn and +0x56 keeps counting up (obj1+0x16a80 to +0x16aa7). The other viewer sees the same through the racer draw (racer +2 = 2). For the humans +0x56 is not advanced by the animation-counter routine (it is skipped for racers when [0x28be2], or racer 1 in the race: obj1+0x1626a to +0x16281). So each human's counter advances once per drawn frame of its own viewer.
2. **Round-end test**, only on the frames where the page word [0x28b24] == 0x3e80 (obj1+0x21241; so every second frame) and one of the two wreck flags (car 0 +0x7e = obj2+0x848e, car 1 +0x7e = obj2+0x8592) is set (obj1+0x21252 to +0x2126a):
   * both wrecked: text "THAT WAS A DOUBLE KILL!" (shoot-out; "WHAT A CRASH!" in the race), ready when both racer +0x56 (obj2+0xaae6, +0xab4e) exceed 0xc = 12 (obj1+0x2127e to +0x212c5);
   * only car 0 wrecked: when racer 0 +0x56 > 0xc, the text is the name of driver [0x28b96] + " HAS BEEN WAXED!" (obj2+0x1a00); only car 1: the same with [0x28c6a] and racer 1 +0x56 (obj1+0x212ca to +0x213b7). (Wrecked player's name.)
3. **Message:** page [0x28b24] := 0, `0x1a414` draws the box (rows 92 to 107), timer [0x1e720] := 0 and the frame waits until it passes 0x190 = 400 ticks (obj1+0x213c0 to +0x213f2), [0x1e720] := 0, [0x1ec64] := 0, page := 0x3e80. (The tick is the same dword racer-states.md 7.3 calls the 136 Hz counter; about 2.9 s.)
4. **Score (shoot-out only; the two-player race jumps to the restart before this):** `cmp [0x28bdc],0 / jnz 0x2006a` at obj1+0x21411. Then: car 0 wrecked: `inc dword [0x85e4]` (**P2's** score), car 1 wrecked: `inc dword [0x84e0]` (**P1's** score), so a double kill gives both a point; the **survivor/killer is credited, not the victim** (obj1+0x2141f to +0x21439).
5. **End of the match:** ebx = 2 when `[0x84e0] >= [0x1eda0]` or `[0x85e4] >= [0x1eda0]` (the jumps `jnl` at obj1+0x2144a and +0x21457): then sound reset `0x1adc`, the final screen `0x1bbd8` (section 4.6), both score dwords cleared (obj1+0x2146f to +0x21483) and the frame routine returns (jz 0x227aa) to the menu code.
6. **Next round (respawn):** otherwise [0x847c] = [0x8580] = 3 (obj1+0x2148b to +0x21494) and `jmp 0x2006a`: the **whole round setup runs again** (obj1+0x2006a to +0x21021): both players go back to their start positions and headings (racer init `0x6f90`, cameras obj1+0x2051b to +0x205af), all .SPW objects/pickups are restored (`0x113f0` clears the consumed marker; obj1+0x201b6 to +0x201d4), the shot table (61 entries) and the inverted flags cleared (`0x1d4fc`, obj1+0x1d4fc to +0x1d544), the 24 car records reset (wreck flag car +0x7e = 0 at obj1+0x20322, held item +0x16 = 0 and ammo +0x6a = 0 for the two-player modes at obj1+0x2027c to +0x20283, taunt count +0xbc = 0), timers [0x1e720], [0x1ec64] = 0, [0x28c42] = 0, the surface lookups again, the first frame redrawn with the scores (`0x33d8`). **There is no respawn at the place of death.** The score dwords (car +0xd0) are not touched by the round setup (they are cleared only by the menu at obj1+0x10166 and after the last round).
